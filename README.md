# ВышКат — учёт парка кикшеринга

Домашнее задание №1 по КПО: доменная модель и консольное приложение учёта парка «ВышКат»
с применением SOLID, DI-контейнера (Boost.DI) и юнит-тестов (GoogleTest / GoogleMock).

## Сборка и запуск

Нужны компилятор с поддержкой C++17 и CMake ≥ 3.20. Проверено на macOS (AppleClang 21).
При первой конфигурации нужен интернет: GoogleTest скачивается через `FetchContent`.
Boost.DI — один заголовочный файл, он уже лежит в `third_party/boost/di.hpp`.

```bash
cmake -S . -B build
cmake --build build
./build/vyshkat              # приложение
ctest --test-dir build       # тесты
```

Покрытие (нужен `gcovr`, на macOS: `brew install gcovr`):

```bash
cmake -S . -B build-cov -DENABLE_COVERAGE=ON
cmake --build build-cov
ctest --test-dir build-cov
gcovr -r . --filter app/ --exclude app/main.cpp --gcov-executable "xcrun llvm-cov gcov"
```

На Linux с gcc флаг `--gcov-executable` не нужен.

## Что умеет приложение

| Пункт меню | Что делает |
|---|---|
| 1. Добавить устройство | выбор вида, ввод параметров, техосмотр, присвоение инвентарного номера |
| 2. Отчёт | число единиц на балансе и суммарное суточное потребление энергии |
| 3. Список для новичков | прокатная техника с простотой ≥ 6 |
| 4. Инвентарная ведомость | название и инвентарный номер всей техники и вещей |
| 5. Демо-сценарий | автоматически проходит все сценарии, см. ниже |
| 0. Выход | |

Демо-сценарий принимает по одному устройству каждого вида, показывает два отказа на
техосмотре (перерасход энергии и слишком сложная модель) и ошибку некорректных данных
(простота 15), затем выводит все отчёты.

Регламент техосмотра задан в `app/main.cpp`: максимальный расход 2,0 кВт·ч в сутки,
минимальная простота 2. Демо рассчитано на эти значения.

Некорректный ввод не роняет программу: буквы вместо числа просят ввести заново, а
недопустимые значения (простота вне 1–10, отрицательный расход, пустое название)
отсекаются конструкторами модели и выводятся как сообщение об ошибке. Расход можно
вводить и через запятую.

## Структура проекта

```
app/
├── Interface/        IInventory, IEnergy, IEasy, IServiceCenter
├── Base/             InventoryBase, EnergyBase, EasyBase
├── Devices/          ElectricScooter, ElectricBicycle, Bicycle, Helmet,
│                     DockingStation, ChargingCabinet
├── ServiceCenter/    ServiceCenter — техосмотр
├── Park/             Park — хранение и приёмка
├── Report/           Report — отчёты
├── Console/          ConsoleApp — ввод и вывод
└── main.cpp          корень композиции: сборка через DI-контейнер
tests/                юнит-тесты

```

Всё, кроме `Console/` и `main.cpp`, собирается в библиотеку `vyshkat_core`.
Тесты подключают именно её, то есть проверяют тот же код, что работает в приложении.

## Доменная модель

### Интерфейсы: одна способность — один интерфейс

У каждого интерфейса есть свой потребитель, ради которого он существует.

| Интерфейс | Что объявляет | Кто использует |
|---|---|---|
| `IInventory` | `get_name`, `get_number`, `set_number` | `Park` (номер при приёмке), `Report::sheet` |
| `IEnergy` | `get_energy` — суточный расход, кВт·ч | `Report::sum_energy`, `ServiceCenter` |
| `IEasy` | `get_easy` — простота 1–10, константы шкалы | `Report::list_beginners`, `ServiceCenter` |
| `IServiceCenter` | `approve_device` | `Park` |

Интерфейсы не хранят данных. Диапазон шкалы простоты (`IEasy::kMinEasy`, `kMaxEasy`)
записан в интерфейсе как часть контракта и используется и в `EasyBase`, и в `ServiceCenter`.

### Базовые классы

- `InventoryBase` хранит название и номер (`std::optional`), не допускает пустое название,
  разрешает присвоить номер только один раз.
- `EnergyBase` хранит расход и не допускает отрицательное значение.
- `EasyBase` хранит простоту и не допускает значения вне 1–10.

Конструкторы баз защищённые (`protected`): сами по себе они не имеют смысла.
Базы нужны, чтобы хранение и проверка каждой характеристики жили в одном месте,
а новый вид техники собирался из готовых частей.

### Устройства

| Класс | InventoryBase | EnergyBase | EasyBase |
|---|:---:|:---:|:---:|
| `ElectricScooter` — электросамокат | ✓ | ✓ | ✓ |
| `ElectricBicycle` — электровелосипед | ✓ | ✓ | ✓ |
| `Bicycle` — велосипед | ✓ | | ✓ |
| `Helmet` — шлем | ✓ | | |
| `DockingStation` — док-станция | ✓ | ✓ | |
| `ChargingCabinet` — зарядный шкаф | ✓ | ✓ | |

В классах устройств только конструктор: всё поведение унаследовано.
Простота есть только у прокатного транспорта, поэтому «реализует `IEasy`» означает
«прокатная техника», и отдельный признак не нужен.

### Сервисы

- **`ServiceCenter`** решает, принять ли устройство. Отклоняет, если суточный расход
  больше `max_energy` (перерасход — признак неисправности) или простота меньше `min_easy`
  (слишком сложную модель не берут в прокат вообще). Проверка применяется, только если
  у устройства есть соответствующая способность: шлем проходит всегда. Пороги
  включительные и передаются в конструктор, который проверяет их корректность.
- **`Park`** хранит объекты и принимает новые. Порядок в `add`: проверка на `nullptr` →
  техосмотр → присвоение номера → сохранение. Счётчик номеров растёт только после
  успешной приёмки, поэтому отказ не тратит номер.
- **`Report`** считает число единиц, суммарную энергию, список для новичков и ведомость.
  Ничего не печатает, только возвращает данные.
- **`ConsoleApp`** отвечает только за ввод и вывод. Виды устройств описаны в таблице
  `kDeviceKinds`: какие параметры спросить и как создать объект.

### Ключевые решения

- **Номер присваивает система при приёмке.** Номер означает постановку на баланс, поэтому
  отклонённое устройство его не получает. До приёмки номера нет, отсюда `std::optional`.
  Метод `set_number` в интерфейсе — компромисс: его может вызвать кто угодно, но повторное
  присвоение запрещено, а результат помечен `[[nodiscard]]`.
- **Техосмотр проходят все объекты на балансе.** У парка один путь добавления, и не нужна
  отдельная абстракция «транспорт».
- **Правило для новичков находится снаружи устройств**, в `Report`. При изменении правила
  меняется одно место, а классы устройств о нём не знают.
- **Владение.** Устройствами владеет парк (`std::unique_ptr`). Наружу `Park::items()` отдаёт
  `const IInventory*` — доступ только на чтение, без передачи владения. `ServiceCenter`
  хранится как `std::shared_ptr`: его разделяют `main`, контейнер, парк и тесты.
  Там, где объект нужен только на время вызова, используются ссылки
  (`approve_device(const IInventory&)`).

## SOLID

- **S — единственная ответственность.** `Park` хранит и принимает, `ServiceCenter` решает,
  `Report` считает, `ConsoleApp` общается с пользователем. Устройства не знают ни о
  техосмотре, ни о правилах выдачи новичкам.
- **O — открытость для расширения.** Новый вид техники — новый класс из готовых баз и строка
  в `kDeviceKinds`; `Park`, `Report` и `ServiceCenter` не меняются, потому что работают через
  интерфейсы. Новая политика техосмотра — новая реализация `IServiceCenter`.
- **L — подстановка Лисков.** Любое устройство подставляется туда, где ожидается `IInventory`,
  `IEnergy` или `IEasy`, и соблюдает те же инварианты, потому что их проверяют базовые классы.
  Мок `IServiceCenter` подставляется в `Park` без изменений парка.
- **I — разделение интерфейсов.** Три узких интерфейса вместо одного общего. У `Bicycle` нет
  метода `get_energy`, у `Helmet` нет ни энергии, ни простоты. Ни один класс не реализует
  метод, который ему не нужен, и не возвращает «0 вместо ничего».
- **D — инверсия зависимостей.** `Park` зависит от абстракции `IServiceCenter` и получает её
  через конструктор. Какая реализация будет подставлена, решает только `main.cpp`.

## DI-контейнер

Используется [Boost.DI](https://boost-ext.github.io/di/). Вся сборка находится в `main.cpp`:

```cpp
auto service_center = std::make_shared<ServiceCenter>(kMaxEnergy, kMinEasy);

auto injector = di::make_injector(
    di::bind<IServiceCenter>.to(service_center),
    di::bind<Park>.in(di::singleton),
    di::bind<Report>.in(di::singleton));

auto app = injector.create<ConsoleApp>();
```

Контейнер сам строит цепочку `ConsoleApp → Park, Report → IServiceCenter`.

- `ServiceCenter` создаётся вручную, потому что у него числовые параметры, которые контейнер
  не может угадать. Контейнеру отдаётся готовый экземпляр.
- `Park` и `Report` — одиночки, иначе консоль и отчёт получили бы разные парки.
- Классы модели ничего не знают о контейнере. Поэтому из `Report` убран конструктор
  `Report(Park&&) = delete`: он мешал контейнеру выбрать конструктор, а подсказка через
  `BOOST_DI_INJECT` добавила бы в модель зависимость от библиотеки.

## Ответы на обязательные вопросы

### Какой принцип SOLID применён наиболее явно и где?

**ISP.** Каждая характеристика из ТЗ вынесена в свой интерфейс (`IInventory`, `IEnergy`,
`IEasy`), и у каждого есть свой потребитель: ведомость, отчёт по энергии, список для
новичков. Классы реализуют ровно те интерфейсы, которые им нужны (таблица выше).
Отчёт по энергии видит только `IEnergy`, поэтому в сумму попадает всё, что потребляет
энергию, — и транспорт, и вещи, — без знания конкретных классов.

Вторым по явности идёт **DIP**: `Park` зависит от `IServiceCenter`, а не от `ServiceCenter`,
и именно это позволяет подменять техосмотр в тестах.

### Какой принцип сознательно ограничен и почему это приемлемо?

1. **OCP для правила новичков.** Порог задан константой `Report::kBeginnerMinEasy`, без
   отдельного интерфейса политики. Правило одно, и интерфейс с единственной реализацией был
   бы декоративным. Если появится второе правило, оно выделяется в интерфейс и подставляется
   через DI; менять придётся только `Report`.
2. **`dynamic_cast` в `Report` и `ServiceCenter`.** Это проверка типа во время выполнения,
   которую часто считают запахом. Альтернативы хуже: добавить в `IInventory` методы вроде
   «есть ли энергия» — значит вернуть толстый интерфейс, а раскладывать объекты по разным
   спискам при добавлении — значит усложнить парк. Плюс текущего решения: любой новый класс,
   реализующий `IEnergy` или `IEasy`, учитывается в отчётах и техосмотре автоматически.
3. **Нет интерфейса `IPark`.** `Report` зависит от конкретного `Park`. Реализация парка одна,
   а для тестов отчёта достаточно настоящего парка с подменённым техосмотром.

### Что сломается при расширении?

- **Новый вид транспорта** (например, электромоноколесо): новый класс, наследующий
  `InventoryBase`, `EnergyBase` и `EasyBase`, и одна строка в `kDeviceKinds` в `ConsoleApp`.
  `Park`, `Report`, `ServiceCenter` и тесты не меняются; энергия и список для новичков
  учтут новый вид автоматически.
- **Сотрудник** не реализует `IInventory`, поэтому не может попасть в парк, отчёты и
  ведомость. Существующий код не меняется; для учёта сотрудников нужен отдельный класс.
- **Склад запчастей.** Запчасти стоят на балансе, значит, реализуют `IInventory`. Если склад
  хранит их отдельно от парка, придётся менять `Report::sheet`: сейчас ведомость берёт
  объекты только из `Park`. Решение — выделить абстракцию «источник инвентарных объектов» и
  передавать отчёту несколько источников. Это то место модели, которое придётся расширить.
- **Новое правило техосмотра** — новая реализация `IServiceCenter` и одна строка в `main.cpp`.

### Какой тест фиксирует решение техосмотра и правило для новичков? Как подменяется зависимость?

Решение техосмотра:
- `ServiceCenterTest.ApproveDeviceExceedsEnergyLimit` и `ApproveDeviceBelowEasyLimit` — отказы;
- `ServiceCenterTest.ApproveDeviceOnEnergyBoundary` и `ApproveDeviceOnEasyBoundary` —
  пограничные значения принимаются;
- `ServiceCenterTest.ApproveDeviceNoEnergyInterface` — шлем проходит всегда.

Зависимость парка от решения техосмотра:
- `ParkTest.MockDemonstrateDependencyInjection` — мок (GoogleMock) принимает самокат с
  расходом 9999 кВт·ч, который настоящий центр отклонил бы, и парк его принимает. Значит,
  парк полагается на внедрённое решение, а не на собственную логику;
- `ParkTest.AddWithMockServiceCenterRejects` — мок отклоняет, парк остаётся пустым;
- `ParkTest.RejectedDeviceDoesNotConsumeInventoryNumber` — отказ не тратит номер.

Как подменяется зависимость: мок передаётся в конструктор `Park` как
`std::shared_ptr<IServiceCenter>` (внедрение через конструктор). Тест
`DiContainerTest.ContainerInjectsFakeServiceCenterIntoPark` собирает парк тем же
`di::make_injector`, что и `main.cpp`, но привязывает `IServiceCenter` к моку.

Правило для новичков:
- `ReportTest.BeginnerBoundaryEasy6Included` и `BeginnerBoundaryEasy5Excluded` — граница ≥ 6;
- `ReportTest.ListBeginnersFiltersCorrectly` и
  `ReportNoBeginnerTest.ListBeginnersEmptyWhenNoDevicesQualify`.
